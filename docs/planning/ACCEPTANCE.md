# Harniqo 验收与开发执行手册

日期：2026-10-29 · 本文定义验收方法，当前没有应用测试通过记录。

对应 [里程碑](ROADMAP.md) 与 [67 项任务](BACKLOG.md)。正式版本应交付能够连续使用、诊断和恢复的完整流程。模拟 Adapter、假流式输出、只安装成功或只完成页面不构成真实集成验收。

## 1. 每项任务怎样算完成

| 状态 | 必须满足 |
| --- | --- |
| TODO | 已列入计划，尚未实现 |
| IN_PROGRESS | 依赖已核对，正在实现或执行验证 |
| IMPLEMENTED | 代码/配置/文档已提交，必要静态检查和模块验证通过；真实集成尚未证明 |
| VERIFIED | 在声明的真实环境、版本和模型下覆盖本任务的正向、负向和必要故障用例 |
| ACCEPTED | 交付物、相关用例和阶段退出条件齐备，证据可追溯；未解决限制不影响所声明支持范围 |
| BLOCKED | 明确写出缺少的外部资源/能力、受影响项和解除条件；独立任务继续推进 |

模块逻辑用必要单元测试，跨模块用真实集成测试，核心用户流程用黑盒/原生验收，执行边界用实际故障和越界测试。Stub 用来验证错误处理，但不能作为 Harness、VM、OIDC、存储或三端支持的唯一证据。文档修改只核对内容、链接与一致性，不为其添加无意义应用测试。

阶段关闭需要全部必选条件通过；缺签名、原生构建环境、模型权限、隔离执行资源或可恢复备份时不能标记正式发布可用。正常实现和可逆仓库维护按已授予授权推进，不在每项任务后额外等待一次批准。

## 2. 证据记录格式

每个任务在 BACKLOG 执行记录中追加索引，详细报告放在受控存储。公开仓库只放脱敏报告、可公开的用例和引用。

```text
任务 / 状态 / 验收日期：
源码提交 / 镜像 digest / 镜像归档 SHA-256：
客户端、控制面、Runner、Adapter、Harness 与模型版本：
环境 / OS / 架构 / 资源 / 负载：
配置快照 / Manifest ID（如适用）：
执行的验收用例 / 结果 / 未通过原因：
日志、原始事件、截图、产物与测试报告位置：
数据授权与脱敏状态：
已知限制 / 阻塞解除条件 / 下一步：
```

镜像和 VM 写入层位于工作区根目录下的 `images/`，格式与保留见 [镜像规范](../../images/README.md)。不得用相同可变 tag 代替实际 digest。实际服务地址、凭据引用、私有任务输入和用户对话不进入公开报告。

## 4. 实验报告的固定口径

- **有效评分成功率**：在有效评分集合内判定业务成功的 Trial 数 / 获得有效评分的 Trial 数；列明评分采用首次 Attempt 还是预定义最终规则，并同时保留首次结果。
- **全部计划交付率**：评分判定业务成功且所需产物有效可获取的 Trial 数 / 所有计划 Trial 数。完成评分覆盖率另列为“有有效评分的 Trial 数 / 全部计划 Trial 数”，不能把失败报告算成功交付。180-Trial 基线的分母始终为 180；不兼容、跳过、取消和未知不能悄悄消失。
- 故障注入实验必须在 Manifest 标记用途、注入位置和样本；与自然运行基线分开出报告，不用于未经说明的 Harness 效果排名。
- Trial 保留所有 Attempt，重试费用和时间累计；报告同时给首次与最终结果，不能只选成功重试展示。统计规则在实验创建前固定。
- 等待、资源启动、执行、评分与人工等待分开计时。样本数、重复波动、排除项及原因可查；小样本结果不宣称普遍最优。
- 模型、环境、存储与评分费用分别归因；实测、估算和未知分开。预算控制精度与渠道能力一致，在途请求和延迟结算有说明。
- Harness 比较固定共同支持的模型/环境条件，配置组合比较允许各自优化但标明组合。额外网关改写、Agent 委派或工具转换必须保存在 Manifest 中。

## 5. 发布门槛与支持边界

M0 冻结以下表格的实际数值后才能关闭；本次计划不把未测量阈值写成已实现能力。

| 必填项 | 需要确定与测量的内容 |
| --- | --- |
| 系统矩阵 | macOS/Windows/Linux 的具体版本、架构、安装与更新渠道 |
| 负载 | 活动会话、并行 Trial、组织数量、单产物/事件/会话/实验规模 |
| 交互指标 | 平台 API 与事件 p95 延迟、重连补取时间；将上游模型响应时间单列 |
| 故障指标 | 心跳失联判定、待核对时限、可恢复/不可恢复处理、资源回收时限 |
| 数据恢复 | 数据范围、备份频次、保留、异地位置、RPO、RTO 与完整恢复验证频次 |
| 成本与配额 | 可实测渠道、估算渠道、预算预留与停止规则、单任务与总量限制 |
| 兼容窗口 | 客户端/控制面/Runner/Adapter/Harness 支持版本与破坏性更新策略 |

M8 只能发布已验收的范围。内部试用包、正式安装包和线上服务必须标明实际支持状态。三端签名或隔离资源缺失属于发布阻塞；Mock、跳过测试或“后续补齐”不能解除门槛。

## 6. 每次开发的固定动作

1. 选择依赖已通过的任务，核对本计划、相关契约及已有代码；范围变化先更新任务和验收。
2. 记录版本和实际环境，实施完整功能与必要验证；编译/测试/打包前检查 `df`，只清理本任务可重建产物。
3. 对声明支持的真实流程运行验收，包括相应负向与故障场景；保存报告、配置、原始证据和镜像校验信息。
4. 检查差异和敏感内容，提交源码及任务进展；同步服务器。提交不夹带 `.private`、运行镜像或业务数据。
5. 只有验收通过才推进状态；把未通过原因、影响和下一步写明。阶段结束更新剩余工作和估时，继续依赖已满足的下一项。

仓库维护与 MIT 开源方向已由所有者授权。初次规划提交可以直接维护；后续有应用代码时使用符合仓库规则的分支、CI 与合并流程，发布仍以通过本手册门槛为前提。
