# Harniqo 首版验收基线

版本：1.0 · 2026-10-29 · 对应任务：M0-07。

本文把 [技术架构](../architecture/ARCHITECTURE.md) 的初始目标固定为可执行的验收口径，配合 [ACCEPTANCE 用例](../planning/ACCEPTANCE.md) 使用。数值是本项目采用的验收目标，**不是实测结果、生产容量或已提供 SLA**。原生资源、签名、模型、隔离与恢复证据尚未齐备，因此 M0-07 保持进行中，不能因本文已写成而勾选完成。

## 1. 首批 OS / 架构与发行渠道

正式支持采用白名单，不根据“系统版本更高”自动继承。

| 编号 | 首批验收组合 | 发行/升级基线 | 需要的真实证据 |
| --- | --- | --- | --- |
| OS-MAC-A | macOS26，arm64 | 签名并公证的应用与安装包；签名更新元数据 | 原生 arm64 构建、真实 Mac 安装与端到端、稳定签名后的 Keychain/升级行为 |
| OS-MAC-I | macOS15，x64 | 与上项独立验证 Intel 包及更新 | 原生 x64 构建、支持该系统的 Intel Mac 安装/登录/文件/通知/升级 |
| OS-WIN | Windows11 25H2，x64 | 经验证的 Windows 代码签名与安装/更新渠道 | 真实 Windows11 安装、交互流程、凭据存储、升级失败恢复；仅 Windows Server 构建不替代它 |
| OS-LINUX | Ubuntu24.04 LTS，x64 | 受签名/校验保护的 deb/软件源发行渠道 | 真实桌面会话下安装、Secret Service 有/无两种情况、通知、文件、包升级与卸载 |
| EXEC-LINUX | Ubuntu24.04 LTS，x64；KVM/QEMU/libvirt | 经过准入的宿主包与 guest 运行包；镜像可追溯 | 真实 KVM 启停、专用通道、网络/身份隔离、限制、取消和恢复；不能用 TCG 冒充 |

测试使用各固定 OS 家族当时仍受支持的安全补丁，并在报告写入确切 OS build、内核、硬件、Electron 及依赖版本。这里固定了首批范围，不虚构已经测过的补丁号。macOS14+ 曾作为架构兼容设想，**不作为首发生产支持承诺**；macOS27、Windows26H2、Windows/Ubuntu arm64 及其他发行版暂列后续候选，验收前不进入正式白名单。

核验时 Apple 仍发布 macOS15 和26 的安全更新；Microsoft 官方表中 Windows11 25H2 支持至 2027-10-13，24H2 Home/Pro 已于 2026-10-14 结束支持。Ubuntu24.04 LTS 处于标准维护周期。发布前重新核对上游窗口，不能将本日期的状态永久固化。[Apple 安全更新](https://support.apple.com/en-us/100100)、[Windows 生命周期](https://learn.microsoft.com/en-us/lifecycle/products/windows-11-home-and-pro)、[Ubuntu 周期](https://ubuntu.com/about/release-cycle)

每个客户端组合运行 AC-02/06/10/11/17/18/25 中适用的完整流程。三端编译和安装冒烟在 M1 接入，正式签名与完整升级验收在 M8；内部未签名构建只能标注内部测试，不能代替正式包。

## 2. 并发、资源与公平性

| 项目 | 固定初始目标/限制 | 验证方法 |
| --- | --- | --- |
| 活跃订阅 | 100 个已授权 SSE 连接 | 至少10个组织、每组织2个项目；构造并发读取和撤权，不能全部使用同一管理员身份 |
| 执行容量 | 8 个同时占用的 VM slot | 交互、Trial、Verifier、构建 VM 都计入总量；不能单独计算后各启动8台 |
| slot 默认 | 2 vCPU / 4 GiB RAM | guest 与宿主 QEMU 进程均有限额，磁盘/网络有准入与配额；单任务增加资源先检查可分配容量 |
| 预留 | 至少2个交互 slot、2个批量/评分 slot，余下4个按组织公平排队 | 一个组织提交长队列不能长期饿死另一个组织；评分不会被候选执行占满而永远无法启动 |
| 宿主余量 | CPU、内存和实际磁盘可用量各保留至少25% | 验收前记录 `df`、CPU/RAM、实际镜像与运行写入层；不只看 guest 配额或磁盘虚拟容量 |
| 隔离 | 不同组织、未授权 Workspace、不同 Trial/并行候选分离；同一 Workspace 单写者 | AC-03/07/12/13/30，包含 VM 崩溃、宿主失联及旧租约回报 |
| 资源回收 | 已确认终止的孤儿资源在下一轮对账中回收；对账目标周期60s | 活跃资源不误回收；状态不明进入 reconciling，不通过抢回预算强行再次执行 |

报告包含宿主类型、虚拟化支持、控制面与数据服务拓扑、背景负载、磁盘类型/空间和网络。指定开发主机的资源快照只能证明检查时容量，不能证明真实 VM 或 SaaS 已验收。SaaS 的 N−1 可用容量与故障域另作演练，不能把两进程放同一物理宿主当冗余。

## 3. 性能、恢复和撤权

以下为基准负载：100 SSE、总计每秒20条应用事件（普通事件≤2 KiB）、8个资源 slot；控制面与客户端网络 RTT≤100ms，无人为丢包。预热2分钟，稳定负载至少15分钟；普通 API 每类至少1000次请求，结果分类型统计，不能用一个快接口稀释慢接口。

| 指标 | 通过阈值 | 边界与测量 |
| --- | --- | --- |
| 普通元数据 API | 服务端 p95≤300ms | 从服务端接收请求到完成响应，不含模型生成、文件传输和客户端网络；错误率、p99、请求类别一并报告 |
| 活跃事件可见 | 从事务提交到客户端接收 p95≤1s | 两端时钟校准并记录偏差；只统计有正确授权的活跃连接；原始样本保留 |
| 重连补取 | 单 Run 补取1000条、每条≤2 KiB，在5s内完成 | 一致性快照/游标加事件去重，无漏读；游标过期走明确重同步；不将重连当新执行 |
| 授权撤销 | 新命令/审批/下载/续传在撤权提交后拒绝；已有订阅/下载在5s内收敛 | 包含重放旧幂等请求和已有有效 Token；已经下载到用户磁盘的内容无法撤回 |
| Runner 心跳 | 初始周期10s，连续30s无有效续约后进入待核对 | 时间依据平台权威期限和校时；截止不证明实际 VM 已停；Broker watchdog 与真实资源核对必须独立工作 |
| 取消 | 5s内显示已接受/停止中；正常可控 VM 在60s内取得宿主停止证明 | 原生取消失败时升级停 VM；宿主不可达则显示 reconciling 并告警，不能为了达到60s伪造 cancelled |
| 普通进程恢复 | API/Worker 重启后已提交 Run 与命令不丢失，无第二写者 | 单进程故障目标 RPO=0，依赖实际持久事务；不把灾难恢复允许窗口套到普通进程重启 |

未达到时保留失败证据，修正实现/配置或正式更新目标；不能只删除慢请求。故障注入与正常性能结果分别报告。有限标签用于指标，资源 ID 留在日志/trace，避免基数无界。

## 4. 数据、备份与灾难恢复

首版“小型部署”恢复验收数据上限固定为：PostgreSQL10 GiB、对象100 GiB且不超过100000个对象、全部持久 Workspace 实际占用64 GiB、基础镜像归档16 GiB。超过该档必须扩大资源并重新压测/恢复验收，不能继承本档 RTO。

| 项目 | 首版目标与通过条件 |
| --- | --- |
| RPO | 灾难性站点/持久盘丢失后，已备份的受保护数据恢复点距离故障≤15min；报告实际缺失窗口及受影响对象 |
| RTO | 在上述数据规模、已落实的恢复资源与至少200 Mbit/s有效恢复链路下，4h内恢复声明的核心流程；起点为宣告恢复，终点为登录、查询、文件、提交运行和一项评分均通过 |
| 范围 | 业务数据库、对象与Filer元数据、身份数据库、Secret加密存储/恢复材料、原生工作区、配置、镜像清单和必要基础镜像 |
| 位置 | 至少一个独立于开发/生产故障宿主的备份目的地；密钥与备份不能只放同一失效磁盘 |
| 完整性 | 备份加密、hash和访问控制可验证；从独立备份恢复到新环境，不能只核对“备份命令返回成功” |
| 执行权 | 隔离旧控制面，产生新恢复代次并废止旧 grant；确认旧 VM/写者状态后再允许新写入；不能复活数据库回滚出的旧租约 |
| 外部消耗 | 灾难期间可能已发生的供应商调用/工具副作用保留核对入口，不因业务数据回滚而自动重试或当作零费用 |
| 频次 | 上线前完整演练；上线后至少每月完整恢复一次，且每次破坏性迁移/Secret恢复策略变化后补演练 |

普通进程故障与站点灾难不同。上述灾难 RPO 允许的窗口必须透明记录，不能宣传成任何故障都绝无数据损失。对象、密钥、原生状态和数据库的一致性依 AC-01/23/24 验收。

历史与原始轨迹默认保留30天；产物、输入快照、实验与审计的具体保留按组织配置及适用的数据要求执行，并在安装时显式确认。变更保留策略不得绕过进行中的运行、追溯和备份销毁规则；M7 需落实删除与恢复说明。本文不为未知客户数据作统一法定保留承诺。

## 5. 模型、预算与实验条件

- M0-03 要求两个获准且可替换的真实模型端点，每个记录 model ID、endpoint、参数、凭据引用和允许费用；真实密钥只进私有秘密存储/受限文件，不进任务或仓库。
- 首批至少三种 Harness 按能力证据正式准入。Octop 服务、Octop Harness 和外部委派分别记录，不把“许可开放”算作能力通过。
- 模型请求可完整代理时采用预留/校验/结算；每次新操作重新检查执行授权、恢复/租约代次和预算。评分、重试、VM 与在途调用均计入。
- 直接 BYOK 或用量不可观测渠道显示 estimated/unknown，使用明确时长/步数/并发/上游配额限制，不能承诺精确费用硬封顶。固定预算数额来自组织授权配置，不替用户编造可消费金额。
- 180-Trial 验收按20任务×3候选×3重复；自然基线与故障注入分开，保留所有 Trial/Attempt、有效评分成功率、全部计划成功交付率、评分覆盖率和累计成本。
- 比较任务使用合成或明确获准的输入，固定成功条件、隐藏评分材料与清单版本。独立 Verifier 不持有候选的执行身份或可写评分材料。
